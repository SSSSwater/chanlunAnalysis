# 更新日志书写规范

## 目的

更新日志面向实际使用者，只说明版本带来的可见功能和体验变化。它不是提交记录、开发任务清单或技术变更说明。公告内容统一维护在项目根目录的 `update-log.md`，后端读取并解析后由前端展示。

## 版本格式

- 当前版本使用 `v主版本.次版本.修订号`，例如 `v1.1.01`。
- 主版本和次版本使用一位数字；同一版本线的修订号使用两位数字。
- 已经归档的功能版本可省略修订号，例如 `v1.1`、`v1.0`。
- 日志按版本号从新到旧排列，当前版本必须单独显示在弹窗顶部。
- 日期统一使用 `YYYY-MM-DD`。

## Markdown 文件格式

- 根目录文件名固定为 `update-log.md`。
- 文件使用 `## v版本号 - YYYY-MM-DD` 表示一个版本。
- 每个版本使用一个 `###` 标题概括功能范围。
- 用户可见内容使用无序列表，每一条以 `-` 开头。
- 每条描述一个独立或紧密相关的功能、体验变化，按功能分别列点。
- 版本按新到旧排列，第一条记录就是当前版本。

```markdown
# 更新日志

## v1.1.03 - 2026-08-26

### 首页指数加载

- 首页优先展示已有指数数据，打开更快。
- 页面加载完成后自动更新指数数据。
```

## 内容规范

- 只写用户能看到、使用或直接感受到的变化，优先说明“改了什么”和“使用后得到什么结果”。
- 每条控制在一句话内，使用简短、明确的动词，例如“支持”“新增”“显示”“减少”“恢复”。
- 一个版本只保留一个日志条目，同一主题的修复、补充和体验优化合并为一句话。
- 一个功能涉及多个独立结果时，按用户关注的功能分别列点。
- 标题概括本版的功能范围，不要把实现方式写进标题。
- 不写代码、接口、文件名、函数名、数据表、缓存、部署、测试、重构、依赖和内部数据处理等实现细节。
- 不把数据源切换、回退策略等技术过程作为公告主体；只有当数据来源本身是用户可见功能时，才简短说明用户能看到的结果。
- 避免使用“优化若干问题”“修复多个 bug”等无法说明用户收益的空泛表述。
- 不写面向开发者的操作说明、版本发布过程或致谢内容。

## 示例

```markdown
## v1.1.01 - 2026-08-25

### 首页指数延迟加载与后台刷新

- 无结构候选时改为紧凑显示。
- 首页换手率榜单去掉正号，并简化最近分析标题。
```

## 发布前检查

1. 确认当前版本只在 `update-log.md` 的最新日志条目中出现一次对应定义。
2. 确认每个版本只有一个标题，并且每条内容只对应一个独立或紧密相关的功能、体验变化。
3. 确认最新版本排在最前，旧版本没有重复描述同一变更。
4. 删除实现细节，只保留用户能直接理解的功能和体验结果。
5. 通读每条内容，确认不依赖开发背景也能理解用户获得了什么变化。
